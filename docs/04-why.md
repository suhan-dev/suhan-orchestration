# 04. 왜 이렇게 하는가

## 문제

1. **최상위 모델 토큰은 비싸고 한도가 있습니다.** 주간·월간 사용 한도가 있는 요금제에서는 최상위 모델을 어디에 쓰느냐가
   곧 며칠을 일할 수 있느냐입니다.
2. **하청은 메인 모델을 물려받습니다.** Claude Code의 `general-purpose`·`Explore`·`Plan`, Codex의 `default`·`worker`·`explorer`처럼
   모델을 따로 정하지 않은 하청은 부모 세션의 모델로 돕니다. 메인을 최상위 모델로 열어 두면 하청도 최상위 모델이 됩니다.
3. **팬아웃은 폭주합니다.** 다중 에이전트 모드(Claude Code의 Workflow/ultracode, Codex의 `ultra`)는 한 번에 하청을 여럿 띄우고,
   하청이 또 하청을 띄우면 수가 곱으로 늘어납니다.
4. **규칙만으로는 지켜지지 않습니다.** 지침 파일에 "하청은 싼 모델로"라고 써 두어도, 모델은 긴 세션에서 잊거나 "이번만" 하며 어깁니다.

실제로 메인급 모델로 하청을 수십 건 띄워 주간 사용 한도의 절반을 며칠 만에 쓴 사고가 있었습니다. 이 저장소는 그 뒤에 만든 장치를
일반화한 것입니다.

## 원칙

- **생각하는 쪽과 실행하는 쪽을 나눕니다.** 메인은 설계·판단·종합·사용자 문안을 맡고, 하청은 이미 정해진 일 하나를 정확히 수행합니다.
- **역할은 세 개로 고정합니다.** 실행(executor), 국소 난제(deep-reasoner), 잡무(runner). 역할을 늘리지 않으면 규칙과 게이트가 단순해집니다.
- **모델·강도는 사람이 정합니다.** 역할마다 어떤 모델을 어떤 강도로 쓸지는 터미널에서 사람이 정하고, 정의 파일이 그대로 적용합니다.
  모델은 호출 때 `model`·`effort`를 바꾸지 못합니다(게이트가 막음).
- **규칙은 훅으로 강제합니다.** 지침은 설명이고, 강제는 PreToolUse 훅이 합니다. 훅은 오류가 나면 통과시켜(fail-open) 세션을 마비시키지 않습니다.
- **켜고 끌 수 있어야 합니다.** 일반 모드가 필요한 날이 있습니다. 한 명령으로 규칙과 게이트를 함께 끕니다.
- **모델이 나와도 손대지 않습니다.** 하청 모델은 계열 이름(별칭)으로 적어 두고, 새 버전은 도구가 해석하거나(Claude) 로컬 sync가 바꿉니다(Codex).
  이 과정에 LLM 토큰은 들지 않습니다.
- **규칙 문서는 짧게.** 켜져 있는 동안 매 세션 지침에 들어가므로 4~5 KB로 유지하고, 모델에게 버전 확인 같은 일을 시키지 않습니다.

## 위임 절차(규칙 문서에 들어 있는 것)

1. 작업을 서로 독립인 단위로 쪼갭니다. 단위 하나 = 목적 하나.
2. 단위마다 하청 하나(세션당 동시 1개가 기본).
3. 지시문에 목표 · 대상 파일/범위 · 완료 기준 · 검증 방법 · 보고 형식을 넣습니다.
4. 결과는 메인이 검토하고 종합합니다.
5. 실패하거나 전제가 깨지면 그대로 재시도하지 않고 다시 나눕니다.

## 왜 Claude Code와 Codex를 같이 다루나

두 도구 모두 "하청 정의 파일 + PreToolUse 훅 + 전역 지침"이라는 같은 뼈대를 가집니다. 같은 원칙을 같은 명령(`oche`)으로 다루면,
어느 쪽을 쓰든 같은 습관으로 일할 수 있고, 한쪽 한도가 바닥났을 때 다른 쪽으로 옮겨 가기도 쉽습니다.
